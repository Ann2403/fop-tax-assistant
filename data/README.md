# Дані для витягу (ДЗ 1)

30 «брудних» повідомлень від ФОП до бухгалтера або податкового помічника і 10 розмічених вручну відповідей (golden set).

## Звідки тексти

Тексти **синтетичні**. Їх написано за мотивами типових питань з бази знань ДПС (ЗІР) і тематичних ФОП-спільнот, без копіювання реальних повідомлень. Персональних даних немає: імена, назви компаній і суми вигадані, номери рахунків та ІПН замасковані (`****`). Реальні виписки й листи сюди не потрапляють — для них є `data/private/` (у `.gitignore`).

## Структура

| Шлях | Що |
|---|---|
| `texts/tNN.txt` | Сирий текст повідомлення |
| `manifest.csv` | `id`, `received_at` (дата отримання — від неї рахуються відносні дати), `channel`, довжина, чи входить у golden set, які «пастки» містить |
| `golden/tNN.json` | Еталонний `FopRequest` (схема — `src/fop_tax_assistant/schema.py`) |

## Що робить тексти «брудними»

- Довжина від 16 символів («єсв 3 кв скільки») до довгого ланцюжка листів з цитатами й підписом.
- Мови: українська, російська, англійська, суржик, суміш.
- Помилки, скорочення, сленг: «3гр», «10.3 ляма», «баксів», «скок».
- Шум OCR: літери `О` і `З` замість цифр `0` і `3`.
- Пропущені поля: немає групи, періоду або дат.
- Пастки класифікації: переказ власних коштів, «повернення позики», подарунки від родичів, комісія банку, продаж валюти.
- Тексти поза темою і prompt injection (`t25`).

## Правила розмітки

Ці правила — одночасно інструкція для розмітника і основа для промпту.

**`intent`** — головна дія, яку просить користувач. Якщо дій кілька, береться перша зі списку:
1. `declaration_prep` — підготувати або перевірити декларацію;
2. `calculation` — порахувати суму податку чи внеску;
3. `deadline` — питає лише про строки;
4. `documents` — надсилає документи без питання;
5. `tax_question` — питання про правила;
6. `out_of_scope` — не стосується податків ФОП.

**`fop_group`, `vat_payer`** — лише якщо прямо сказано в тексті («3 гр», «без ПДВ», «пдв нема»). Не вгадувати.

**`period`** — звітний період, про який запит. «3 кв» без року → рік з `received_at`. «З початку року» → `quarter: null`. Місяць → його квартал. Якщо період не названо — `null`, навіть якщо його можна вивести з дат транзакцій.

**`transactions`** — конкретні рухи коштів із сумою:
- сума завжди додатна, напрям — у `direction`;
- відносні дати («вчора») рахуються від `received_at`; дата без року — рік з `received_at`; невідома дата — `null`;
- агреговані суми («дохід за квартал 410 000») — **не** транзакції;
- продаж валюти — `outgoing` у проданій валюті, `counterparty_type: bank`;
- сплата податку чи ЄСВ — `outgoing`, `tax_authority`;
- рахунок або акт з датою оплати — одна `incoming` транзакція на дату оплати.

**`counterparty_type`**:

| Значення | Коли |
|---|---|
| `client_resident` | українська компанія або ФОП |
| `client_nonresident` | іноземний клієнт або платформа (Upwork) |
| `own_account` | переказ власних коштів |
| `individual` | фізособа не як клієнт (родичі, позика) |
| `bank` | банк, комісія, обмін валюти |
| `tax_authority` | податкова, сплата податків |
| `unknown` | неможливо визначити |

**`topics`** — лише те, про що користувач **прямо питає**, а не все згадане. Для `documents` без питання і `out_of_scope` — `[]`.

**`missing_fields`** — що потрібно для `intent`, але відсутнє в тексті:
- `calculation`, `declaration_prep`: потрібні `fop_group` і `period`; `vat_payer` — лише якщо група 3; `amounts` — якщо немає жодної суми; `transaction_dates` — якщо в будь-якої транзакції `date: null`;
- `deadline`: потрібен `period`;
- для решти — завжди `[]`.

**`language`** — мова більшої частини тексту; `mixed`, якщо друга мова займає помітну частину (від ~20%).

**`description`** — коротка нотатка, у метриках не враховується.

## Golden set

Розмічено 10 текстів: `t01 t03 t04 t05 t07 t08 t09 t11 t16 t29`. Вони покривають усі `intent` (крім `deadline`), усі 4 мови, OCR, відносну дату, агреговану суму та неоднозначні транзакції.

Чернетку розмітки підготовлено за правилами вище, а потім **перевірено вручну** — після перевірки кожного файлу познач його в чеклісті:

- [ ] t01 · [ ] t03 · [ ] t04 · [ ] t05 · [ ] t07
- [ ] t08 · [ ] t09 · [ ] t11 · [ ] t16 · [ ] t29

`tests/test_golden.py` перевіряє, що кожен golden-файл валідний за схемою і збігається з `manifest.csv`.
